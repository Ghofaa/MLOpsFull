# Monitoring Step Mini Report (Structured Logging + Drift Detection)

## 1) Scope of this step

This section documents the monitoring-related additions made to the ML serving layer.  
The objective was to introduce practical production monitoring by:

- centralizing logs in a dedicated directory,
- adding statistical data drift detection during inference,
- recording drift alerts for operational follow-up.

These additions complement CI/CD by extending automation beyond deployment into post-deployment observability.

---

## 2) Files touched and why

### `madewithml/config.py`

Used to centralize logging paths and ensure persistent log storage.

Implemented behavior:

- define a project-level logs directory (`LOGS_DIR`),
- create it automatically if missing (`mkdir(parents=True, exist_ok=True)`),
- route logger outputs to rotating `info.log` and `error.log`.

Why it matters:

- creates durable evidence of runtime health,
- supports debugging and incident analysis,
- enables reportable monitoring artifacts for deliverables.

### `madewithml/serve.py`

Used to add runtime drift monitoring to prediction flow.

Implemented behavior:

- load a baseline reference dataset from `X_train_reference.npy`,
- initialize `KSDrift` with `p_val=0.01`,
- extract simple numeric monitoring features from incoming requests,
- run drift checks during `/predict/`,
- append warning entries to `logs/error.log` when drift is detected.

Why it matters:

- detects distribution shifts between training and production traffic,
- provides an actionable signal for retraining or investigation,
- turns serving endpoint into an observable production component.

---

## 3) Functional description of added logic

### 3.1 Drift detector initialization

On service startup:

1. Try to load `X_train_reference.npy` from project root.
2. If present, initialize `KSDrift(reference, p_val=0.01)`.
3. If absent, continue serving but disable drift checks and log a warning.

Design choice:

- graceful degradation avoids hard service failure when reference data is missing.

### 3.2 Feature extraction for monitoring

Incoming text payload is converted into a lightweight numeric matrix:

- `title` length,
- `description` length.

These features are sufficient to demonstrate drift mechanics in a school project while remaining fast at inference time.

### 3.3 Drift check during prediction

For every `/predict/` request:

1. Build feature vector from request payload.
2. Run KS-based drift test against reference distribution.
3. If drift detected (`is_drift == 1`), write warning with timestamp and p-values to log.
4. Continue normal prediction flow.

This ensures monitoring is non-blocking and does not interrupt inference service availability.

## 4) Contribution to CI/CD and MLOps lifecycle

These changes strengthen the pipeline in the following way:

- **CI contribution**: monitoring logic becomes testable code included in pull-request validation.

- **MLOps contribution**: introduces feedback loop (deploy -> observe -> alert -> retrain decision).

In other words, CI/CD is no longer only about "build and deploy", but also about "deploy and monitor safely."

## 6) Validation checklist (for demo/report evidence)

1. Service starts with valid run ID and model checkpoint.
2. Startup log confirms drift detector initialization (or warns reference missing).
3. `/predict/` endpoint returns predictions normally.
4. Drifted input windows produce warning entries in `logs/error.log`.
5. No inference outage occurs when drift check runs.

Suggested evidence screenshots:

- console startup logs,
- prediction API response,
- `error.log` drift warning line with timestamp and p-values.

---

## 7) Limitations and future improvements

Current implementation is intentionally lightweight:

- monitoring features are coarse (text lengths only),
- no automatic retraining trigger yet,
- no dashboard integration (Grafana/Prometheus) yet.

Recommended next improvements:

1. use richer embedding-based drift features,
2. add drift-rate threshold alerting policy,
3. trigger retraining pipeline automatically when sustained drift is detected,
4. publish drift metrics to a monitoring dashboard.

---

## 8) Conclusion

This step successfully adds practical production monitoring to the serving system through centralized logs and statistical drift detection.  
It improves reliability and observability of the deployed ML service and provides clear artifacts for CI/CD deliverables and presentation.
